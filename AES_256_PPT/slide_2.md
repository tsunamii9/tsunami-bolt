# Slide 2 — What Encryption Actually Promises

## 🎯 Objective

By the end of this slide, everyone should understand that encryption isn't just about hiding data. Modern encryption can provide three important guarantees—confidentiality, integrity, and authenticity—but it still has clear limits.

---

# 🗣️ Opening

When most people hear the word **encryption**, they immediately think:

> "It hides my data."

That's true, but it's only one piece of the puzzle.

Good encryption is really about **trust**.

Can I trust that nobody read my data?

Can I trust that nobody changed it?

Can I trust that it came from someone who actually knew the secret key?

These are three different questions, and each has its own guarantee.

---

# 🔒 Confidentiality — "Nobody else can read it."

Imagine placing a letter inside a locked box.

The delivery person can carry it.
Someone could even steal the box.

But without the key, the contents remain unreadable.

That's confidentiality.

It protects the **contents** of the message while it is travelling or being stored.

Notice something important:

The existence of the message isn't hidden.

People can still see that you're sending a message.

They just can't understand what's inside it.

---

# 🛡️ Integrity — "Nobody can secretly change it."

Now imagine you've sent an API request to transfer money.

Originally, the request says:

```json
{
  "to": "Alice",
  "amount": 10000
}
```

If an attacker intercepts the request and changes the amount to **100000**, the receiver should immediately detect that something has been modified.

That's integrity.

It answers one simple question:

> **"Is this exactly the same data that the sender created?"**

If even a single bit changes, integrity verification should fail.

---

# ✅ Authenticity — "It really came from someone who knows the secret."

Now imagine someone creates their own API request pretending to be your mobile application.

The request might look perfectly valid.

But if they don't possess the correct secret key, they cannot generate a valid authentication tag.

The server can immediately reject it.

Authenticity doesn't tell us **who** the person is.

It tells us the message was created by **someone who possessed the expected cryptographic secret**.

For AES-GCM, this assurance comes from the **authentication tag**.

---

# ⚠️ What Encryption Doesn't Promise

One of the biggest misconceptions in application security is confusing **authenticity** with **authorization**.

Encryption can prove that:

* the message wasn't modified, and
* it was created by someone who possesses the correct key.

But it **never decides whether that caller is allowed to perform the requested action.**

That's the responsibility of your application.

For example,

An authenticated request might ask:

> "Transfer ₹50 lakh."

Encryption can prove the request is genuine.

It **cannot** decide whether that user is actually allowed to transfer ₹50 lakh.

That decision belongs to:

* Authentication
* Authorization
* Business Rules
* Access Control

Those remain the API's responsibility.

---

# 🌍 Real-world Example

Let's use a UPI payment as an example.

When you pay someone using a banking app:

* **Confidentiality** protects your account details, customer identifiers, and other sensitive information while the request travels across the network.
* **Integrity** ensures nobody can modify fields such as the destination account or transaction details without detection.
* **Authenticity** gives the bank confidence that the request was generated by a trusted application using the correct cryptographic keys.

Notice what encryption **doesn't** do.

Even if the request is perfectly encrypted and authentic, the bank must still verify:

* Is this customer logged in?
* Does this account have sufficient balance?
* Is the transfer limit exceeded?
* Is this user authorized to perform this transaction?

Those are application-level security checks—not encryption.

---

# 💡 Key Message

Encryption protects the **message**.

Your application protects the **business**.

Confusing those two responsibilities is one of the most common security mistakes.
